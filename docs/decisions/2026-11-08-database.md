# Database design (P1-03, widened to the whole project)

Date: 2026-11-08. Card: P1-03 (C1 req 7, PD5). Package: w1-database. Asked in the w1-database build session and confirmed final by the master session, to which the Owner handed build questions (2026-11-08).

## Decisions

| # | Question | Owner's answer |
|---|---|---|
| DB1 | Where do the database files live? | Migrations in `frontdoor/supabase/migrations/`, code in `frontdoor/db/`. |
| DB2 | How does the server talk to Supabase? | A direct Postgres connection through Supabase's session pooler (IPv4), with the `postgres` npm package. Not the Data API. Reason: transactions for Stripe event dedupe, and the tests run the same SQL. |
| DB3 | What may a student's own login read straight from the database? | Nothing. RLS on every table, no allow rules, and no table rights for `anon` and `authenticated`. Only the server reads and writes. |
| DB4 | What happens to the trial record on day 91? | Keep a keyed hash of the email and Stripe's card fingerprint, with no tenant link, so the same email or card cannot start a second trial. The privacy policy (T5), which Claude drafts and the Owner approves, must state this kept record (D32). |
| DB5 | The table plan | Approved as listed in `frontdoor/db/README.md`: 17 tables and the `tenant_overview` view. Both email reports start off. The alert threshold must stay below autopause. |

## Changes asked for by the metering package (w1-metering), same day

- `model_usage.cache_write_1h_tokens`: the 1-hour part of `cache_write_tokens` (which stays the total). A 1-hour cache write costs 2x the input rate and a 5-minute one 1.25x, so without the split a stored row cannot be priced again for the C7 cross-check with upstream.
- `model_usage.cost_usd` may be null. Metering reports the Owner decided (2026-11-08) that a call to a model missing from Pi's price list goes through and is stored with no dollar amount. Null rows add nothing to the cost sums, so they never count toward the alert or autopause; `usageTotals` reports them as `unpricedCalls`.
- `recordSearch` defaults the fee to Tavily's $0.008 (C3 req 7), since the proxy records only tenant and time.

## How it was tested

- **PGlite** (`@electric-sql/pglite`, Postgres 17 compiled to WebAssembly, in-process) runs in `npm test` and CI with no server. Every migration applies to a fresh database in each test file.
- The RLS tests check two layers on every table: `anon` and `authenticated` are refused outright, and even when a grant is added by mistake, RLS returns none of tenant B's rows (none at all) to tenant A's login. `service_role` sees both tenants.
- The test roles copy older Supabase projects, where new tables in `public` are granted to `anon` and `authenticated` by default. The migrations take those rights away themselves, so the lockdown holds on either kind of project.
- A second check, `tests/frontdoor-db-postgres.test.ts`, runs the migrations and the module on a real Postgres 18 server through postgres.js. It skips in CI. It passed on the local WSL server on 2026-11-08.

## Not in the database (later cards decide)

- The Owner's model settings template (C3 settings sync). The front door decides where it lives.
- The trial limits: 2 hours (C2 req 2) and the $10 backstop (PD2) stay in code.

## Open points for later cards

- **P2-05:** after the Owner unpauses a tenant whose 30-day cost is still above $89, the next metered call would pause it again. P2-05 must decide how an unpause holds (for example, until the cost drops below the threshold, or for a set time). The schema may need a column then.
- **P4-02:** the email hash needs a server secret (a Railway variable, for example `LH_TRIAL_HASH_KEY`). Changing it later makes earlier claims unmatchable.
- **Hardening option:** the server could log in as its own Postgres role with only table rights, instead of the `postgres` owner role. Not done now.
